## 澄清：重定向循环与登录接口无关

在副本上实测各 URL 变体（端口 18084）：

| 请求 | 结果 |
| --- | --- |
| `/user/userLogin?name=cyr&pwd=123456` | 200 JSON，正常 |
| `/user/userLogin` | 200 JSON，正常 |
| `/user/userLogin/`（尾斜杠） | 302 → `/login.jsp` → 循环 |
| `/User/userLogin`（大写） | 302 → 循环 |
| `/user/userlogin`（小写 l） | 302 → 循环 |
| `/`、`/index.html`、`/favicon.ico` | 302 → 循环 |

**结论**：`/user/userLogin` 的 anon 是精确匹配，拼写一致就放行。循环一定由**另一条被 `/**` 拦到的请求**点起——最常见是浏览器自动发的 `/favicon.ico`、或地址栏输入的 `/`。
`login.jsp` 是 Shiro 302 的**目标地址**（响应），不是用户请求过的地址，这是最容易误判的点。
诊断手法：F12 → Network → Preserve log → 看第一个 302 的发起请求。

**配置建议**：`addPathDefinition("/user/userLogin","anon")` 过于脆弱，建议改 `/user/**`（注意 `/user/logout` 要排在它前面）。

## 密码加密存储方案（教学，主人明确要求不改其代码）

用项目真实 classpath 运行 `%TEMP%\PwdDemo.java` 实测：

```
new SimpleHash("md5","123456",ByteSource.Util.bytes("yuqn"),1).toHex()
  = d9d29476fe3fc6ae73386b1b86c377e6   (32 字符)
库里存密文 + 输入 123456  -> matcher.doCredentialsMatch = true
库里存密文 + 输入 654321  -> false
库里存明文 + 输入 123456  -> false          ← 当前问题根源
盐顺序: hash(salt+pwd)=d9d29476... vs hash(pwd+salt)=ec5962ee...  不等
iterations: 1 -> d9d29476... / 2 -> 643f576b... / 1000 -> 2dae4863...
同输入结果稳定可重现
```

**核心公式**：`密文 = hash(算法, 盐 + 明文, 迭代次数)`，盐在**前**。

**两条落地路线**：
- 固定盐：在 `UserService.register` 里用与 `ShiroConfig` 相同的算法/盐/次数算 `toHex()` 入库。
- 随机盐（推荐）：`user` 表加 `salt` 列、`User` 加字段，注册时 `UUID` 生成盐，`MyRealm` 改用 `ByteSource.Util.bytes(user.getSalt())`。

**三处参数必须一致**，这是唯一易错点：入库的 `SimpleHash` / `ShiroConfig` 的 matcher（算法+迭代次数） / `MyRealm` 返回的盐。
另注意 matcher 的 `storedCredentialsHexEncoded` 默认 `true`，对应 `toHex()`；若改存 Base64 需同步调整。

## 概念澄清：加盐哈希到底防住了什么

主人问「加盐加密存储是不是防数据库泄露」。结论要点：

- **术语**：这是**哈希/摘要**（单向不可逆），不是「加密」（可逆）。第一性原理：系统本身不需要知道用户密码，只需要能验证，所以不存可逆的东西。
- **盐不保密**：盐与摘要同库存放，泄露时一起被拿走。盐的作用是**防批量**——破彩虹表、阻断「破一个 = 破全部」、阻断按「多人共用弱密码」挑目标。成本从 O(1) 变 O(用户数)。
- **盐防不住弱密码和快算法**：攻击者只需猜一个→用同盐同算法算→比对。
- **真正抗泄露靠慢哈希**（bcrypt/scrypt/Argon2）+ 随机盐 + 强密码策略三层叠加。

### 实测数据（用项目真实 classpath，同一台机器单线程）

```
md5 + 1 次迭代   :   535 ns/次  ≈ 187 万次/秒
bcrypt (cost 10) : 51.3 ms/次  ≈    19 次/秒
单次代价倍数     : 约 9.6 万倍
穷举 62^8 单线程 : md5 3.7 年 / bcrypt 35 万年（GPU 对 md5 还有 3~4 个数量级加成）
bcrypt 输出样例  : $2y$10$hH8EXO7Hq2F2ojimBM5wZuIGCfpEm7l30UgiElqp.a0uKwEFrYsbO（60 字符）
同密码两次生成必不同 -> 盐是内置随机盐，不需要单独存 salt 列
```

### Shiro 3.0.1 换慢哈希的真实难度（已实测，纠正易误判的预期）

| 事实 | 证据 |
| --- | --- |
| `HashedCredentialsMatcher` 只吃 JDK MessageDigest 算法 | `md5`/`sha256`/`sha512` 构造成功；`bcrypt`/`argon2` 抛 `UnknownAlgorithmException: No native 'xxx' MessageDigest instance available` |
| shiro-hashes-bcrypt / shiro-hashes-argon2 确实随 starter 进 classpath | `BCryptHash`、`Argon2Hash` 类可 Class.forName 加载 |
| 但这两个类是**包内可见（非 public）**，外部包无法直接调用 | javap 输出无 public 修饰符；直接编译报「不是公共的」 |
| 且这两个模块**没有** `META-INF/services/org.apache.shiro.crypto.hash.HashSpi` 注册文件 | 只有 shiro-crypto-hash 注册了 `SimpleHashProvider` |
| `DefaultHashService.computeHash` 传任何算法名都抛 `UnsupportedOperationException` | 实测 md5 也失败，说明该 SPI 路径在此配置下不通 |

**结论**：在 Shiro 里换 bcrypt/argon2 **不是改一个字符串**，需要自己写 `CredentialsMatcher`（底层接 `BCryptPasswordEncoder` / jBCrypt 等）。仅作演示可用反射 `setAccessible(true)` 调包内静态方法，生产不可取。
