## 初始管理员账号的建法（教学结论）

**核心原则**：账号可以手动插，但**摘要绝不能手算/手抄** —— 必须由「与登录校验同一套参数」的代码生成。
手抄的真实风险不是抄错字符，而是**参数对不上**（算法 / 盐 / 迭代次数任一处不同结果就完全不同，且登录只报「用户名或密码错误」，极难排查）。

三条路线：

| 路线 | 做法 | 适用 |
| --- | --- | --- |
| A 一次性算 + UPDATE | 跑个 main / 测试用 `SimpleHash` 打出摘要，复制进 SQL | 学习期最快 |
| B 启动时初始化 | `CommandLineRunner` 查库→不存在才 create（幂等） | 推荐，正规 |
| C 走注册接口 | 补完 `userRegister`，调接口建号 | 最贴近真实链路 |

**分水岭**：一旦改成**每用户随机盐**，路线 A 彻底失效（盐与摘要必须成对写入，手抄无法保证配对），只能走 B 或 C。
原则提炼：**只要涉及随机值，就必须让程序自己写库，人只负责触发。**

生产注意：默认密码别硬编码（走配置/环境变量）、首次登录强制改密、初始化逻辑必须幂等。

**未修改主人任何文件**，仅编译验证 + 示例代码。

## 结论：doGetAuthorizationInfo 当前未被调用（懒回调）

主人判断「只做登录、没用权限控制，所以 doGetAuthorizationInfo 没起作用」——方向对，准确说法是**没被调用**（不是坏了）。

**机制**：`AuthorizingRealm` 的两个回调是「谁问谁触发」，不是并列执行。

| 回调 | 触发源 |
| --- | --- |
| `doGetAuthenticationInfo` | `subject.login(token)` |
| `doGetAuthorizationInfo` | `hasRole/hasAllRoles/isPermitted/isPermittedAll`、`checkRole/checkPermission`、过滤链 `roles[..]/perms[..]`、`@RequiresRoles/@RequiresPermissions`、JSP `shiro:` 标签 |

**三处证据**：
1. 全项目 grep `hasRole|isPermitted|checkRole|Requires*|roles[|perms[` → **0 处**。
2. `ShiroConfig` 过滤链只有 `anon` / `logout` / `authc`，无 `roles`/`perms`。
3. 独立 demo（`%TEMP%\AuthzTriggerDemo.java`，用项目自身依赖）：login 期间该方法调用 **0 次**；之后 hasRole/isPermitted 各问一次即触发一次。

**现状说明**：`MyRealm.doGetAuthorizationInfo` 里的 `info.addRole("yuqn")` / `addStringPermission("user:add")` 是**硬编码 mock**，至今从未被读取过。

### 两个前瞻性坑（已提醒主人）
- `UnauthorizedException extends AuthorizationException`（**不是** `AuthenticationException`）。`UserController` 只 catch 了 `AuthenticationException`，将来加权限控制后 `checkRole` 失败会直接冒泡成 500 —— 与最初那个 Shiro 未装配的 500 属同一类问题。需单独处理（全局异常处理器）。
- **没有授权缓存**：starter 3.0.1 的 `AutoConfiguration.imports` 里**无任何 cache 相关自动配置**。不自己注册 `CacheManager` 的话，每次问权限都会真查一次库。
- 好消息：`ShiroAnnotationProcessorAutoConfiguration` 已在 starter 注册，`@RequiresRoles` 等注解**开箱可用**。

```java
addPathDefinition("/user/userRegister","anon");
addPathDefinition("/error","anon");     // 必须，否则任何 404/500 都会变重定向循环
```

修复后实测结果（全绿）：

| 用例 | 结果 |
| --- | --- |
| 注册新用户 | `{"code":200,"msg":"success","data":"注册成功"}` |

## 2026-10-13（下午）过滤链顺序实验 + 会话机制 + 两个坑

### 过滤链顺序规则（反编译 + 四组实测确认）

`PathMatchingFilterChainResolver.getChain()` 字节码：遍历 `getChainNames()`，`pathMatches` 为真即
返回该链 —— **First-Match-Wins，命中即止，规则冲突不报警**。`pathMatches` 委托 `PatternMatcher`；
另有 `removeTrailingSlash`（尾斜杠会被裁掉，`/x/` 与 `/x` 等效）。
`caseInsensitive` 默认 false → **大小写敏感**。

| 场景 | 写法 | 结果 |
| --- | --- | --- |
| 1 | `userRegister=anon` 在 `/**=authc` 前 | 注册 200 ✅ |
| 2 | `/**=authc` 在最前 | 注册/logout/登录 全 302 ❌ |
| 3 | `/user/**=anon` 在 `/user/logout=logout` 前 | logout 404，且**登出后会话仍有效** ❌ |
| 4 | `/user/logout=logout` 在 `/user/**=anon` 前 | logout 302，真被接管 ✅ |

**结论**：越具体越靠前，`/**` 永远最后。

### 会话机制（实测 Subject 状态）

| | 登录前 | 登录后 |
| --- | --- | --- |
| `isAuthenticated` | false | **true** |
| `getPrincipal` | null | `st5668` |
| Session | 未创建 | 已创建，id `D75BC3A5…` |
| Cookie | 无 | `JSESSIONID=D75BC3A5…; Path=/; HttpOnly` |

- 登录状态的实体是**服务端 Session**；`JSESSIONID` 只是钥匙，不含身份信息。
- 每请求：读 Cookie → 找回 Session → 取 `isAuthenticated` → authc 据此放行/拦截。
- `hasRole("yuqn")` 在登录后返回 **true**，验证了 `doGetAuthorizationInfo` 的懒触发。

### 发现的两个坑

1. **登出后会话仍然有效**（场景 3 实测：登出后访问受保护资源仍 200）。
   `/user/logout` 返回 **404**，说明 `logout` 过滤器**没有真正接管**该路径。
   需查明：`/user/logout` 在过滤链中的实际匹配情况，以及 `logout` 与 `anon` 的交互。
2. `UserController.userRegister` 是 `@PostMapping`，浏览器地址栏访问必得 **405**（主人已遇到）。
   计划把 `userLogin` 与 `userRegister` 统一改为 `@PostMapping`（同时消除密码进 URL 的隐患）。
